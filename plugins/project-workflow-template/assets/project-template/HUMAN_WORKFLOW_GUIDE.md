# 인간 운영 가이드

이 문서는 플러그인으로 초기화된 프로젝트에서 사람이 직접 판단하고 승인해야 하는 업무 흐름을 설명한다. 폴더 경계와 Codex의 강제 규칙은 `AGENTS.md`가 정본이다.

## 1. 한눈에 보는 구조

```text
수신 → 01_INBOX → 사람의 분류 지시 또는 Codex 분류안 승인
                    ├─ 02_SOURCE: 외부 기준자료·불변 원본
                    ├─ COMMUNICATION_LOG: 소통 원문·첨부
                    ├─ 03_WORK: 분석·계산·초안
                    └─ 05_MEETING: 회의 기록

03_WORK → 사람의 검토·실제 송부/공식 공유 → 04_OUTPUT
업무 증거 → Codex의 SOT 반영안 → 사람의 diff 검토·승인 → 공식 SOT
재사용 교훈 → 06_KNOWLEDGE/CANDIDATES
```

| 위치 | 역할 | 수정 원칙 | 최종 판단자 |
|---|---|---|---|
| `01_INBOX` | 급히 받은 미분류 자료 | 분류 전 임시 보관 | 사람 |
| `02_SOURCE` | 외부 기준자료 | 배치 후 원본 수정 금지 | 사람 |
| `02_SOURCE/COMMUNICATION_LOG` | 소통 원문·첨부와 파생 요약 | 원문 불변, 요약만 갱신 가능 | 사람 |
| `03_WORK` | 분석·계산·초안·수정본 | 작업 범위 안에서 수정 가능 | 사람 |
| `04_OUTPUT` | 실제 송부·공식 공유한 정확한 파일 | 기존 발행본 불변 | 사람 |
| `05_MEETING` | 안건·회의록·결정·후속 조치 | 공식 자료는 OUTPUT 경로로 참조 | 사람 |
| `06_KNOWLEDGE/CANDIDATES` | 재사용 가능 지식 후보 | 후보별로 근거를 누적 | 사람 |
| `SOT/SourceOfTruth.md` | 현재 공식 프로젝트 상태 | 최초 작성 후 승인형 변경 | 사람 |

## 2. 새 프로젝트 초기화

플러그인을 설치했다면 새 폴더에서 다음처럼 요청한다.

```text
$initialize-project-workspace로 이 폴더의 초기화 계획을 보여줘.
```

Codex가 보여준 경로와 생성 목록을 확인하고 별도 메시지로 승인한다. 플러그인을 사용할 수 없으면 먼저 설치·연결하고 같은 절차를 사용한다.

현재 프로젝트나 로컬 참조 폴더 전체를 복사해 새 프로젝트를 만들지 않는다. 플러그인을 먼저 설치하고, 빈 대상 루트에 대한 읽기 전용 계획과 fingerprint를 확인한 뒤 별도 메시지로 승인한다.

초기화된 루트 하나만 프로젝트 수준으로 사용한다. 기존 프로젝트 하위에는 독립 프로젝트를 초기화하지 말고, 별도 운영 경계가 필요하면 현재 프로젝트와 나란한 새 루트를 선택한다.

1. Codex에서 플러그인으로 초기화한 프로젝트 루트를 연다.
2. Codex 설정과 `project_scout` 실제 호출을 확인한다.
3. 프로젝트 로컬 훅의 명령을 검토하고 신뢰한다.
4. 최초 SOT를 직접 작성할지 승인형으로 작성할지 선택한다.
5. 실제 프로젝트 자료를 받은 뒤 INBOX 분류를 시작한다.

### 기존 워크폴더의 운영 규칙 교체

다음처럼 요청하면 기존 `AGENTS.md`와 `.agents/skills`를 교체하기 전 비교 계획을 받을 수 있다.

```text
$migrate-project-workspace로 이 워크폴더의 AGENTS.md와 로컬 스킬 교체 계획을 보여줘.
```

승인하면 기존 운영 파일을 워크폴더 밖의 `_project-workflow-backups/<프로젝트명-경로해시>/<시각>`에 먼저 복사하고 해시를 확인한 뒤 교체한다. SOT와 업무자료는 변경하지 않는다. `README.md`, 이 가이드, 훅, 누락 폴더는 사람이 명시적으로 선택한 경우에만 동기화한다.

복원할 때도 먼저 계획과 충돌 목록을 확인한다. 마이그레이션 이후 사람이 수정한 운영 파일이 있으면 추가 승인 없이는 덮어쓰지 않으며, 복원 후에도 외부 백업은 남겨 둔다.

### 사람이 최초 SOT를 직접 작성

최초 초기화 직후에만 `SOT/SourceOfTruth.md`의 플레이스홀더를 직접 교체한다. 상단 identity 필드인 `Project ID`, `Project name`, `Workspace type`, `Company workspace ID`, `Status`, `Owner`, `Last updated`를 고정된 순서로 채우고, 목적, 사실, 현재 작업, 최신 발행본, 결정, 미해결 사항, 다음 작업을 실제 값으로 바꾼다. `Workspace type`은 `standard-project`로 유지하고 사용하지 않는 예시는 제거한다.

### Codex가 최초 SOT 반영안을 작성

다음처럼 요청한다.

```text
현재 자료를 근거로 최초 SOT 반영안을 만들어줘. 공식 SOT는 아직 수정하지 마.
```

Codex는 공식 경로를 반영안으로 복제한 뒤 반영안만 수정한다. Codex에 표시된 diff와 전체 반영안 파일을 확인하고, 만족할 때 별도 메시지로 `SourceOfTruth_반영안.md 내용대로 적용`이라고 승인한다. 플레이스홀더는 공식 이력으로 보관하지 않는다.

일부 플레이스홀더만 바꿨다면 직접 작성 중인지 승인형으로 전환할지 먼저 명확히 지시한다.

## 3. INBOX 분류

`01_INBOX`는 급해서 먼저 파일을 넣어 두는 임시 상자다. 오래 보관하는 정본 위치가 아니다.

| 자료 성격 | 기본 목적지 |
|---|---|
| 규격, 발주자료, 외부 도면, 받은 데이터 | `02_SOURCE` |
| 이메일, 메신저, 전화 메모, 캡처와 첨부 | `02_SOURCE/COMMUNICATION_LOG/CNN_yyyy-mm-dd_topic` |
| 내부 계산, 분석, 작성 중 문서 | `03_WORK/WNN_yyyy-mm-dd_topic` |
| 정식 회의 안건, 회의록, 결정, 후속 조치 | `05_MEETING` |
| 실제 송부·공식 공유가 확인된 파일 | `04_OUTPUT/OUTNN_yyyy-mm-dd_topic` |

### Codex에게 분류안 받기

```text
01_INBOX를 확인하고 원본, 제안 목적지, 분류 이유와 해시가 포함된 분류안을 보여줘. 승인 전에는 이동하지 마.
```

분류안에서 다음을 확인한다.

- 소통 첨부가 해당 원문과 같은 `CNN`에 묶였는가
- 서로 다른 소통이 합쳐지지 않았는가
- 날짜가 파일 수정일이 아니라 실제 소통일에 근거하는가
- 작업본이나 미송부 초안이 OUTPUT으로 제안되지 않았는가
- 목적이 불명확한 파일이 이동 보류로 표시됐는가

확인 후 `이 분류안대로 적용`이라고 승인한다. Codex는 이동 전후 SHA-256과 파일명을 검증한다.

### 사람이 정확히 지시하기

```text
01_INBOX/A.pdf를 02_SOURCE/설계기준/A.pdf로 분류해.
```

원본과 목적지를 정확히 지정한 현재 지시는 그 이동에 대한 승인이다. 목적지 폴더나 소통일이 불명확하면 Codex는 필요한 부분만 다시 제안한다.

## 4. 작업과 검토

1. 새 작업 묶음은 `WNN_yyyy-mm-dd_topic`으로 만든다.
   - 병렬 작업이면 작업 흐름마다 서로 다른 `WNN`을 만들고 담당자와 통합 인계 대상을 정한다.
2. 외부 원본을 고쳐야 하면 `03_WORK`에 작업본을 만든다.
3. 계산과 판단에는 근거 경로와 가능한 경우 페이지·시트·셀·조항을 기록한다.
4. 원문 사실, 작업 가정, AI 판단을 구분한다.
5. 사람이 계산 결과, 최신 파일, 대외 표현, 수신자와 송부 범위를 확인한다.

병렬 분석·작성 작업자는 자신의 `WNN` 작업본만 수정하고 결과·근거·미해결 충돌을 통합자에게 인계한다. `01_INBOX` 분류와 `02_SOURCE/COMMUNICATION_LOG` 기록은 해당 승인형 절차의 단일 담당자만 수행하며, `SOT/REVIEW/SourceOfTruth_반영안.md`와 `04_OUTPUT`은 한 번에 한 명의 지정된 통합자/작성자만 수정한다.

요청할 때 목적, 대상 파일, 완료 조건과 수정 허용 범위를 함께 주면 검토가 쉬워진다.

```text
이 계산서를 검토해줘. 원본은 수정하지 말고 오류 후보와 근거 셀만 알려줘.
```

## 5. 소통과 회의

- 소통 원문과 첨부는 한 번 `COMMUNICATION_LOG`에 들어가면 영구 원본이다.
- `<CNN폴더명>_summary.md`는 결정, 행동, 변경, 대기 또는 위험이 있을 때만 만든다.
- 인사나 단순 진행 공유만 있는 소통에는 억지로 요약을 만들지 않는다.
- 회의 초대·녹취 원문·후속 확인 메일은 `COMMUNICATION_LOG`에 둔다.
- 회의 안건·회의록·결정·후속 조치 기록은 `05_MEETING`에 둔다.
- 공식 공유할 회의자료의 초안은 `03_WORK`에 두고, 실제 공유본은 `04_OUTPUT`에 발행한다.

회의 Markdown에는 공식 파일을 복제하지 않고 다음처럼 경로를 남긴다.

```md
2026-07-23 설계회의에서 사용한 공식 송부본은 다음 위치에 있다.

`04_OUTPUT/OUT03_2026-07-22_설계회의자료송부/발표자료.pptx`
```

## 6. 발행본 관리

1. 병렬 작업에서는 `04_OUTPUT`을 기록할 통합자/작성자 한 명을 먼저 지정한다.
2. 사람이 실제 송부 또는 공식 공유 여부를 확인한다.
3. 지정된 통합자가 공유한 정확한 파일을 새 `OUTNN_yyyy-mm-dd_topic`에 보관한다.
4. 날짜는 작업 완료일이 아니라 실제 송부·공유일을 쓴다.
5. SOT에는 파일 경로와 송부일, 수신자 또는 공식 공유 근거를 기록한다.
6. 수정하여 다시 보냈다면 기존 OUT을 덮어쓰지 않고 새 OUT을 만든다.

`04_OUTPUT`에 파일이 있다는 사실만으로 발행을 추정하지 않는다. 소통 기록이나 사람이 확인한 송부 사실이 함께 있어야 한다.

## 7. SOT 승인

최초 초기화 이후 Codex는 공식 SOT를 직접 수정하지 않는다.

병렬 작업에서는 지정된 SOT 통합자/작성자 한 명만 활성 반영안을 수정한다. 다른 작업자는 자신의 `WNN`에 제안과 근거를 남기고 반영안을 읽기 전용으로 취급한다.

1. Codex가 공식본을 `SOT/REVIEW/SourceOfTruth_반영안.md`로 복제한다.
2. 복제본 해시가 공식본과 같은지 확인한다.
3. Codex가 반영안만 수정하고 변경 diff를 표시한다.
4. 사람이 diff, 전체 반영안, 근거 경로, 미해결 사항을 확인한다.
5. 사람이 명시적으로 승인한다.
6. Codex가 기존 공식본을 HISTORY에 보관하고 승인된 반영안을 적용한다.
7. 적용 검증이 모두 끝난 뒤 반영안을 제거한다.

반영안을 바꾸면 이전 승인은 무효다. 필요하면 `수정`, `보류`, `폐기`를 명시한다. 과거 SOT 복원도 과거 파일을 새 반영안으로 복사한 뒤 같은 승인 절차를 따른다.

## 8. 지식 후보

프로젝트 상태와 재사용 교훈을 섞지 않는다. 지식 후보는 `06_KNOWLEDGE/CANDIDATES/KNN_yyyy-mm-dd_topic.md`로 기록한다.

```text
이 작업에서 다른 프로젝트에도 쓸 수 있는 지식 후보를 보여줘. 아직 기록하지 마.
```

```text
검토한 후보를 06_KNOWLEDGE에 기록해줘.
```

같은 원리의 추가 근거는 기존 후보 파일에 누적하고 다른 원리는 새 `KNN` 파일로 만든다. 후보는 공식 표준이 아니며 외부 지식 저장소로 승격하려면 사람이 별도 목적지와 요청을 지정한다.

## 9. 업무 종료 점검

- 원본과 기존 발행본이 수정되지 않았는가
- 프로젝트 수준의 `AGENTS.md`와 공식 SOT가 루트에 각각 하나뿐인가
- 병렬 작업이 서로 다른 `WNN`으로 분리되고 SOT·OUTPUT 통합자/작성자가 한 명으로 지정되었는가
- INBOX에 분류가 필요한 파일이 남았는가
- 최신 작업본과 최신 발행본을 구분했는가
- 실제 송부·공유 근거가 있는가
- 회의 기록이 공식 OUTPUT을 올바르게 참조하는가
- 상태·결정·대기·다음 작업이 바뀌어 SOT 반영안이 필요한가
- 재사용 가능한 교훈을 `06_KNOWLEDGE` 후보로 남길 가치가 있는가
- 검증 실패나 사람이 확인할 불확실성을 완료로 표현하지 않았는가

Stop 훅의 경고는 SOT보다 나중에 바뀐 후보를 알려줄 뿐이다. 실제 SOT 변경 필요성은 사람이 증거와 반영안을 보고 결정한다.
